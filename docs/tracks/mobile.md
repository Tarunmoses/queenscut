# Mobile track

## Status

Expo (SDK 57, TypeScript) app matching the locked design where mockups exist. 4 bottom tabs (Home, Inventory, Expenses, Reports), full Create Order 3-step wizard, order detail/status editing, inventory stock list + add form, expenses list + add form, reports with live metrics. Online-only — talks to the real backend over `fetch`, no offline storage wired up yet. Viewed via Expo Go on a physical phone (no emulator installed on this machine).

Home screen was reworked (2026-10-02) per user feedback to declutter the two most-used flows (Create Order and, next, Capture Expense): the order list was removed from Home entirely and moved to a new dedicated `SearchOrdersScreen`; "+ New Order" is now the single largest, most visually dominant element on the screen (72px, shadowed); a "🔍 Search / View Orders" button sits below it; the stat row grew from 2 to 3 tiles (Active / Pending / **Due Today** — chosen over Overdue/Pending-Payment/Completed as the most actionable daily-glance number, ties to the "Today's Orders" header).

## Context

- **Design is the source of truth — always pull exact markup, don't eyeball colors from memory.** The locked screens live in a design canvas artifact (`https://claude.ai/code/artifact/b9ef64b8-d502-42d8-b80a-f589edc2f266`, also reachable via the short link `https://claude.ai/artifact/PxgejkpCXRUiYwhyU8bCrZ`). Reading it with the `Artifact` tool returns the *canvas editor's own* CSS as the page head — that's a red herring, not the app's design. The real per-screen content is JSON-escaped inside `<script type="application/json" id="appifact-doc">` as one `.dc.html` string per artboard (`MobileHome.dc.html`, `MobileCreateOrder.dc.html`, etc. — list all artboard names with a regex over the saved file: `/"([A-Za-z0-9_]+\.dc\.html)":"/g`). Extract and unescape (`JSON.parse('"' + raw + '"')`) before reading. Don't guess screen layout from the 5 brand colors alone — the actual mockups encode tab bar structure, button heights, badge color rules, etc. that aren't derivable from the palette.
- **Navigation structure matches the mockups exactly, not the original spec text:** 4 tabs only — Home, Inventory, Expenses, Reports, emoji icons, no labels, inactive at 0.5 opacity. "Create Order" is NOT a tab; it's reached via Home's "+ New Order" button into a stack (`HomeStack`: Home → CreateOrderStep1 → CreateOrderStep2 → AddItem (modal, add/edit) → CreateOrderReview → back to Home; also Home → ViewOrder). The original project brief said "Tab navigation: Home, Create Order, Inventory, Expenses, Reports" — that's superseded by the actual locked mockups once they were read.
- **Status badges are a 3-tier solid-fill scale, confirmed by cross-referencing `MobileHome`, `MobileCreateOrderStep3`, and `MobileInventoryStock`:** mild (pink bg `#E8C1D1` / mauve text `#6B4C5C`) → caution (gold bg `#D4AF77` / cream text `#FAF7F2`) → urgent (mauve bg `#6B4C5C` / cream text `#FAF7F2`). These are named `badgeMildBg/Text`, `badgeCautionBg/Text`, `badgeUrgentBg/Text` in `@queenscut/shared`'s `colors.ts` — distinct from the separate green/amber *tint* pairs (`success`/`successBg`, `warning`/`warningBg`) used only for dashboard stat tiles, not badges. The source mockups are NOT fully internally consistent (e.g. "Pending" order status is styled mild/pink on the Step3 review card but caution/gold on the Home list) — where they disagreed, a judgment call was made and is encoded in `src/components/StatusBadge.tsx`: `OrderStatus.PENDING` → urgent ("Not Started"), `IN_PROGRESS` → mild, `COMPLETE` → green success tint (confirmed separately from the web screens' "Complete"/"Paid" styling, not part of the 3-tier scale). `PaymentStatus` and `InventoryStatus` map the same three tiers directly to their 3 enum values with no inconsistency in the source.
- **Measurement form fields are real tailoring fields, not placeholders:** shoulder, front/back neck depth, bust/chest, armhole, sleeve length/round, top length (upper body); waist, hip, thigh, full length (lower body) — see `src/screens/createOrder/measurementFields.ts`. Taken verbatim from `MobileAddItem.dc.html`. `OrderItem.measurements` is a free-form `jsonb` on the backend, so new fields don't need a migration.
- **No native `<select>` in RN** — built `SelectField` (`src/components/SelectField.tsx`) wrapping `@react-native-picker/picker`: inline dropdown on Android, a bottom-sheet modal on iOS (standard pattern since the wheel picker is too tall to show inline).
- **Expo SDK auto-handles npm-workspace monorepo resolution since SDK 52** — `metro.config.js` is just `getDefaultConfig(__dirname)`, no manual `watchFolders`/`resolver` overrides. This was verified in-session (not assumed): an earlier attempt at the old manual config made `expo-doctor` fail with a "metro config mismatch", and fetching `https://docs.expo.dev/guides/monorepos/` confirmed SDK52+ dropped the need for it entirely. `mobile/AGENTS.md` (generated by the scaffold) is the standing reminder to check current docs rather than trust training data for any Expo/RN API — read it before touching navigation, SQLite, or other Expo-adjacent code.
- **Networking for Expo Go (no emulator on this machine):** phone and dev PC must share Wi-Fi; `mobile/.env`'s `EXPO_PUBLIC_API_URL` points at the PC's LAN IP (not `localhost`) — find it with `ipconfig` on Windows if the network changes. Windows Firewall already had an Allow rule for Node on the network's "Public" category, so no firewall changes were needed on this machine; a different machine/network may need one.
- **Known gaps vs. the locked design** (tracked here so they don't get silently forgotten):
  - `ViewOrderScreen` shows items without per-item completion (✓/⚠) or material-source (Supplied/From inventory) — not in the backend data model yet (see [backend track](./backend.md)).
  - Reports' "Trends"/"Inventory" tabs are present as segmented options but show a placeholder — no backend data to back them yet. (Inventory's "History" tab is now real — see below.)
  - No sign-in/sign-up flow (`MobileSignIn`/`MobileSignUp`/`MobileSplash` mockups exist, unimplemented) — app opens straight to the tab navigator.
  - Home's "multiple customers in this order" checkbox from `MobileCreateOrder.dc.html` was intentionally omitted — the backend has no concept of multi-customer orders.
- **Unique order ID is a derived short code, not a new field:** `shortOrderId(id)` in `@queenscut/shared` (`orderId.ts`) takes the first 6 hex chars of the existing UUID, e.g. `#3A7BFF` — no migration, no new counter/sequence. `matchesOrderId(id, query)` is the matching counterpart used by every search surface. Shown in `SearchOrdersScreen`, `ViewOrderScreen`'s header subtitle, and `OrderSearchPicker`.
- **`OrderSearchPicker` (`src/components/OrderSearchPicker.tsx`) is the one reusable "smart search" component**, per explicit user request for a single search bar (order ID or customer name) that also surfaces sub-orders. Two modes via the same component: `mode="linkOrders"` (multi-select with checkboxes, used by Add Expense's "Link to Orders") and `mode="pickSuborder"` (tapping a specific order-item row immediately returns `{orderId, orderItemId}`, used by Add Expense's material-line picker). Both modes always render each order's items underneath it — that's the "show the order and sub-orders" part of the request, not an expand/collapse affordance.
- **Add Expense redesigned again, simplified to one mode at a time** (the combined "Link to Orders" + "Materials Used" screen from the previous round was itself reported as too complicated). Now opens with a 3-way `SegmentedTabs`: **Inventory** / **Consumable** / **Other**. Inventory mode is a strict sequence per explicit user instruction — select inventory item → quantity (its label dynamically shows that item's own `unitType`, e.g. "Quantity (Spools)" vs "Quantity (Meters)", since items have different units) → select order & sub-order via `OrderSearchPicker` (pickSuborder mode) → Amount, which is **read-only by default, auto-computed as qty × item.costPerUnit**, with an explicit "Override amount" checkbox that unlocks manual editing (previously described as "auto-fill" in an additive sense; this round's instructions were more specific: read-only unless overridden). Only a *single* inventory-usage line per expense now (no more multi-line batch) — simpler, matches "give an option on top" framing; log a second expense if more than one material was used. Consumable and Other share the same simple form (description/amount/date + optional multi-order link via `OrderSearchPicker` linkOrders mode); the only difference is Consumable defaults `category` to `"Consumable"`.
- **Order actions are now explicit buttons, not inline-editable fields** — per user: "all actions will have buttons rather than it being editable once I click order". `ViewOrderScreen`'s status/payment are now read-only badges with "Edit Status"/"Edit Payment" buttons opening a new reusable `OptionPickerModal` (radio list + explicit Save — nothing commits on tap-to-select alone). Order items are tappable rows → new `OrderItemDetailScreen` (view amount, design notes, filled-in measurements) with its own "Edit Measurements" (→ new `EditMeasurementsScreen`, reuses the same measurement-field data as the create-order wizard) and "Edit Amount" (→ new reusable `PromptModal`, single-field + explicit Save) buttons. Both new screens call the new backend `PATCH /orders/:id/items/:itemId` (see [backend track](./backend.md)) rather than the order-level `PATCH /orders/:id` with a replacement `items` array — that path would conflict with `InventoryUsage`'s FK constraints.
- Inventory's "History" tab now shows real data via `GET /inventory/usage` (previously a placeholder).
- **App icon + splash screen use the real logo** (`queenscut-ai-artifacts/DESIGN/inkscape_logo/exports/queenscut_png_transparent.png`, 1436×2360, transparent). Per user decision, NOT added to every in-app screen header — just the launch experience, to avoid re-cluttering screens this project just spent several rounds decluttering. Pixel-analyzed the source to separate the monogram (crown+Q, rows 0–1627) from the "QUEEN'S CUT" wordmark (rows 1759+) rather than eyeballing a crop — `mobile/assets/icon.png` and `android-icon-foreground.png`/`android-icon-monochrome.png` use just the monogram (wordmark text is illegible at icon sizes); `splash-icon.png` uses the full tight-cropped lockup. `app.json`'s `expo-splash-screen` plugin takes a transparent, un-padded source image + its own `imageWidth`/`backgroundColor` — baking padding into the source image itself (an earlier attempt) double-pads it. Removed the stale default Expo `android-icon-background.png` (now redundant with `adaptiveIcon.backgroundColor`). **Expo Go cannot show a custom app icon or splash screen** — it's a shared sandbox app; these only render in a standalone/EAS build. Nothing to see in Expo Go today; this is ready for whenever that happens.
- **Order/sub-order screens show expenses logged against them** — no backend changes needed for this: `usageLines` already carry `orderId`/`orderItemId` directly, and `Expense.orders` (now correctly typed in `@queenscut/shared` — it was missing from the type, read-side only, see Worklog) carries the direct links. `src/utils/expenseFilters.ts` has the two filters: `orderLevelExpenses` (linked to the order but with no usage line tied to any of its items — e.g. labor/general cost) and `subOrderExpenses` (has a usage line for that specific item). `ViewOrderScreen` shows order-level first, then each item's expenses grouped underneath (per explicit user ordering); `OrderItemDetailScreen` shows only that item's own expenses. New shared `ExpenseRow` component for consistent rendering in both places.
