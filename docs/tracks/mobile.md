# Mobile track

## Status

Expo (SDK 57, TypeScript) app matching the locked design where mockups exist. 4 bottom tabs (Home, Inventory, Expenses, Reports), full Create Order 3-step wizard, order detail/status editing, inventory stock list + add form, expenses list + add form, reports with live metrics. Online-only — talks to the real backend over `fetch`, no offline storage wired up yet. Viewed via Expo Go on a physical phone (no emulator installed on this machine).

## Context

- **Design is the source of truth — always pull exact markup, don't eyeball colors from memory.** The locked screens live in a design canvas artifact (`https://claude.ai/code/artifact/b9ef64b8-d502-42d8-b80a-f589edc2f266`, also reachable via the short link `https://claude.ai/artifact/PxgejkpCXRUiYwhyU8bCrZ`). Reading it with the `Artifact` tool returns the *canvas editor's own* CSS as the page head — that's a red herring, not the app's design. The real per-screen content is JSON-escaped inside `<script type="application/json" id="appifact-doc">` as one `.dc.html` string per artboard (`MobileHome.dc.html`, `MobileCreateOrder.dc.html`, etc. — list all artboard names with a regex over the saved file: `/"([A-Za-z0-9_]+\.dc\.html)":"/g`). Extract and unescape (`JSON.parse('"' + raw + '"')`) before reading. Don't guess screen layout from the 5 brand colors alone — the actual mockups encode tab bar structure, button heights, badge color rules, etc. that aren't derivable from the palette.
- **Navigation structure matches the mockups exactly, not the original spec text:** 4 tabs only — Home, Inventory, Expenses, Reports, emoji icons, no labels, inactive at 0.5 opacity. "Create Order" is NOT a tab; it's reached via Home's "+ New Order" button into a stack (`HomeStack`: Home → CreateOrderStep1 → CreateOrderStep2 → AddItem (modal, add/edit) → CreateOrderReview → back to Home; also Home → ViewOrder). The original project brief said "Tab navigation: Home, Create Order, Inventory, Expenses, Reports" — that's superseded by the actual locked mockups once they were read.
- **Status badges are a 3-tier solid-fill scale, confirmed by cross-referencing `MobileHome`, `MobileCreateOrderStep3`, and `MobileInventoryStock`:** mild (pink bg `#E8C1D1` / mauve text `#6B4C5C`) → caution (gold bg `#D4AF77` / cream text `#FAF7F2`) → urgent (mauve bg `#6B4C5C` / cream text `#FAF7F2`). These are named `badgeMildBg/Text`, `badgeCautionBg/Text`, `badgeUrgentBg/Text` in `@queenscut/shared`'s `colors.ts` — distinct from the separate green/amber *tint* pairs (`success`/`successBg`, `warning`/`warningBg`) used only for dashboard stat tiles, not badges. The source mockups are NOT fully internally consistent (e.g. "Pending" order status is styled mild/pink on the Step3 review card but caution/gold on the Home list) — where they disagreed, a judgment call was made and is encoded in `src/components/StatusBadge.tsx`: `OrderStatus.PENDING` → urgent ("Not Started"), `IN_PROGRESS` → mild, `COMPLETE` → green success tint (confirmed separately from the web screens' "Complete"/"Paid" styling, not part of the 3-tier scale). `PaymentStatus` and `InventoryStatus` map the same three tiers directly to their 3 enum values with no inconsistency in the source.
- **Measurement form fields are real tailoring fields, not placeholders:** shoulder, front/back neck depth, bust/chest, armhole, sleeve length/round, top length (upper body); waist, hip, thigh, full length (lower body) — see `src/screens/createOrder/measurementFields.ts`. Taken verbatim from `MobileAddItem.dc.html`. `OrderItem.measurements` is a free-form `jsonb` on the backend, so new fields don't need a migration.
- **No native `<select>` in RN** — built `SelectField` (`src/components/SelectField.tsx`) wrapping `@react-native-picker/picker`: inline dropdown on Android, a bottom-sheet modal on iOS (standard pattern since the wheel picker is too tall to show inline).
- **Expo SDK auto-handles npm-workspace monorepo resolution since SDK 52** — `metro.config.js` is just `getDefaultConfig(__dirname)`, no manual `watchFolders`/`resolver` overrides. This was verified in-session (not assumed): an earlier attempt at the old manual config made `expo-doctor` fail with a "metro config mismatch", and fetching `https://docs.expo.dev/guides/monorepos/` confirmed SDK52+ dropped the need for it entirely. `mobile/AGENTS.md` (generated by the scaffold) is the standing reminder to check current docs rather than trust training data for any Expo/RN API — read it before touching navigation, SQLite, or other Expo-adjacent code.
- **Networking for Expo Go (no emulator on this machine):** phone and dev PC must share Wi-Fi; `mobile/.env`'s `EXPO_PUBLIC_API_URL` points at the PC's LAN IP (not `localhost`) — find it with `ipconfig` on Windows if the network changes. Windows Firewall already had an Allow rule for Node on the network's "Public" category, so no firewall changes were needed on this machine; a different machine/network may need one.
- **Known gaps vs. the locked design** (tracked here so they don't get silently forgotten):
  - `ViewOrderScreen` shows items without per-item completion (✓/⚠) or material-source (Supplied/From inventory) — not in the backend data model yet (see [backend track](./backend.md)).
  - Inventory's "History" tab and Reports' "Trends"/"Inventory" tabs are present as segmented options but show a placeholder — no backend data to back them yet.
  - No sign-in/sign-up flow (`MobileSignIn`/`MobileSignUp`/`MobileSplash` mockups exist, unimplemented) — app opens straight to the tab navigator.
  - Home's "multiple customers in this order" checkbox from `MobileCreateOrder.dc.html` was intentionally omitted — the backend has no concept of multi-customer orders.
