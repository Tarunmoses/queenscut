# Backend track

## Status

Core REST API is running against local Postgres: CRUD for customers, orders (with nested items), inventory, and expenses, plus inventory consumption tracking (`inventory_usage`) linked to orders/order-items and optionally to an expense. No auth yet. Not deployed anywhere — runs locally only (`npm run dev:backend`).

## Context

- **Stack:** NestJS + TypeORM + `pg`, `class-validator` DTOs, `@nestjs/config` for env. Module-per-domain under `backend/src/modules/`.
- **Derived fields, not stored redundantly:** `Order.totalAmount`/`balanceDue`/`paymentStatus` are computed server-side in `OrdersService` from the order's items + advance — never trust a client-supplied value for these except as an override. `CustomersService.getSummary()` computes totalSpent/paid/pendingBalance from the customer's orders on read, not as stored columns, so they can't drift out of sync with order edits.
- **SSL config:** `app.module.ts` and `src/database/data-source.ts` (used by the TypeORM CLI) both read `DATABASE_SSL` from env independently — they drifted out of sync once already (see 2026-10-02 entry below). If you touch DB connection config, check both.
- **Enums live in `@queenscut/shared`:** `OrderStatus`, `PaymentStatus`, `InventoryStatus` are defined once in `shared/src/types.ts` and imported into TypeORM entities — don't redefine them backend-side.
- **Known data-model gap vs. the locked mobile design:** `MobileViewOrder.dc.html` (the locked design) shows per-item completion status (✓ done / ⚠ attention) and a material-source distinction ("Supplied" vs "From inventory") on each order item — neither exists on `OrderItem` today. Mobile's `ViewOrderScreen` currently omits both. Adding them means a new migration (`OrderItem.itemStatus` enum + `OrderItem.materialSource` enum) plus DTO/service updates.
- **No auth/users table yet** — `MobileSignIn`/`MobileSignUp` mockups exist in the design but there's nothing backend-side for them (no `User` entity, no guards, no JWT). Every endpoint is currently open.
- **Inventory consumption (`InventoryUsage`, `backend/src/modules/inventory/entities/inventory-usage.entity.ts`)**: a usage row always belongs to exactly one `InventoryItem` + one `Order` + one `OrderItem` (all `ON DELETE RESTRICT` — you can't delete an item/order/order-item that has consumption history), and optionally one `Expense` (`ON DELETE SET NULL` — deleting the expense keeps the consumption record and the stock deduction it already caused). `InventoryService.recordUsage()` is the only way to create one: it validates `quantity <= current stock` (throws `BadRequestException` otherwise), decrements the item, recomputes its status, and snapshots `unitCost`/`totalCost` at time of use so later price changes don't rewrite history. `ExpensesService.create()` calls it per `usageLines[]` entry and unions each line's `orderId` into the expense's `orders` relation alongside any explicit `orderIds` — so an expense can be linked to orders two ways (direct pick, or implicitly via a material line) and both show up the same way on read. **Not supported yet:** editing `usageLines` after an expense is created (would mean reversing+redoing stock deductions) — `ExpensesService.update()` deliberately ignores that field.
- The locked design (`MobileInventoryUsage.dc.html`/`WebInventoryUsage.dc.html`) only specified a *read-only* "Usage History" view — there was no input form in the design at all for logging consumption. The whole create-side flow (linking usage to an expense, auto-decrementing stock, the `GET /inventory/usage` endpoint) was designed fresh this session per explicit user request, not matched against a mockup.
- **`ExpensesService.create()` runs in one DB transaction** (`expensesRepository.manager.transaction(...)`) and `InventoryService.recordUsage()` accepts an optional `EntityManager` to participate in it. This was a real bug found and fixed in session: the original version saved the expense unconditionally *before* processing `usageLines`, so a usage line that failed validation (e.g. insufficient stock) left a saved expense row with no matching stock deduction — found while testing, left 3 orphaned rows in the demo database, cleaned up manually via SQL (see `DATABASE_LOG.md`). Usage lines are processed in a sequential loop, not `Promise.all`, so two lines for the same item can't race on the same stock read-then-write.
- **`PATCH /orders/:id/items/:itemId`** (`OrdersService.updateItem()`) edits a single order item (measurements/apparelType/designNotes/amountCharged) in place and recomputes the parent order's totals — added for the mobile "view/edit sub-order" flow. Deliberately does NOT reuse `update()`'s existing `dto.items` path (delete-all-then-recreate), which is incompatible with `inventory_usage`'s `ON DELETE RESTRICT` FKs (see next bullet) and is unused by the app anyway.
- **Known bug, not yet fixed:** `DELETE /orders/:id` and `DELETE /customers/:id` throw an unhandled 500 (not a clean 4xx) once any order on that customer has `inventory_usage` history — the `ON DELETE RESTRICT` FK has no graceful handling in `OrdersService.remove()`/`CustomersService.remove()`. Found while cleaning up test data through the API and having to fall back to manual SQL instead.

## Next steps

1. Decide on and implement `OrderItem.itemStatus` + `materialSource` (closes the ViewOrder gap above) — note this is conceptually adjacent to but distinct from `InventoryUsage`: materialSource says *where* a garment's material came from, `InventoryUsage` is the actual stock-ledger entry.
2. Add a `User` entity + auth (JWT or session) once the sign-in/sign-up screens are built — currently nothing protects the API.
3. Fix the `DELETE /orders/:id` / `DELETE /customers/:id` 500-on-RESTRICT-FK bug above — at minimum catch the FK violation and return a clean 409/400 ("can't delete, has inventory usage history").
4. When ready to share data across devices (see [database track](./database.md)), swap `DATABASE_URL`/`DATABASE_SSL` to Supabase — no code changes needed, just env + rerunning migrations there.
